# 00 — Project setup and governance

## What we did

We audited the whole app-hub workspace and added four things at the project root: `CLAUDE.md`, `README.md`, `PROGRESS.md`, and this `learn/` folder. No application code changed. What changed is that the project now carries its own context — the objective, the rules, the current state, and the explanations — in files rather than in your head or in a chat window that scrolls away.

## Why

You hit a specific problem: you started this project doing every step manually with Claude chat, learning as you went, and time pressure pushed you to Claude Code. That solves speed but creates two new risks.

**Risk one: drift.** Every Claude Code session starts with no memory of the last one. Without written context, a session has to guess your objective, and guesses compound. You ask for "add a health check", the session doesn't know EKS is the real target, and it optimises for minikube. Three sessions later the project has quietly become something you didn't ask for. `CLAUDE.md` is the fix — it's the file Claude Code reads first, so the objective and constraints are re-established every time.

**Risk two: lost understanding.** If Claude Code just does the work, the project gets built and you don't learn it. That defeats the reason you started. `learn/` is the fix.

The other two files solve older, more ordinary problems. `README.md` answers "what is this and how do I run it" for anyone — including you in six months. `PROGRESS.md` answers "where was I", which matters enormously when you work in bursts separated by days.

There's a general principle here worth naming: **an AI assistant is only as good as the context it has.** Most of the value in setting up a project this way isn't the writing — it's that you've made the context durable instead of ephemeral.

## Key concepts

**1. Context files vs. documentation.** These look similar but serve different readers. `README.md` is documentation — written for humans, describing what exists. `CLAUDE.md` is a context file — written for an AI agent, describing *how to behave*: what to do, what never to do, what to read first. The difference shows up in the writing: a README says "the cluster runs in ap-south-1"; CLAUDE.md says "never run `terraform apply` without asking first, because it starts real billing."

**2. Claude Code auto-loads `CLAUDE.md`.** This isn't a convention we invented — it's built into the tool. A file named `CLAUDE.md` in the working directory is pulled into context at the start of every session, automatically. That's why the objective lives there and not in the README. It's also why it should stay reasonably tight: everything in it costs context budget on every single session.

**3. A "read order" is a context-budget decision.** An AI agent has a finite context window. Reading the wrong things wastes it. This project has a spectacular example: `infra/.terraform/` contains roughly **800 MB** of downloaded provider binaries and third-party module source. It's not your code, it's regenerated by `terraform init`, and it's gitignored. A session that starts exploring there burns its entire budget on files that don't matter. So `CLAUDE.md § 6` states the read order explicitly and forbids that directory by name.

**4. Constraints are about irreversibility.** The rules in `CLAUDE.md § 4` aren't arbitrary caution — they cluster around actions that are expensive or hard to undo. `terraform plan` is free and read-only, so it's unrestricted. `terraform apply` starts billing an EKS control plane and a NAT gateway, so it requires asking. The pattern to internalise: **gate on irreversibility and cost, not on complexity.**

## Walkthrough

### What the audit found

Two structural facts shape everything else in this project, and neither is obvious from looking at the folder.

**Finding 1: there is no root repository.**

```bash
find . -maxdepth 3 -name ".git" -not -path "*/.terraform/*"
```

```
./infra/.git
./links-service/.git
./manifests/.git
```

Three results, and none of them is `./.git`. So `app-hub/` is a plain folder containing three *independent* git repositories, each with its own GitHub remote. This has real consequences:

- A bare `git status` at the root doesn't do what you'd expect. Git walks *upward* looking for a repo, so it either errors or — worse — finds some unrelated parent repo and reports on that.
- Every git command needs an explicit target: `git -C links-service status`.
- A change touching both the service and its manifests is **two commits in two repos**. There's no single commit that captures it atomically.
- The root files we just created (`CLAUDE.md`, `README.md`, `PROGRESS.md`, `learn/`) are in *no* repository. They aren't versioned or backed up. That's tracked as `P-01` in PROGRESS.md and needs a decision from you.

**Finding 2: your toolchain is split across two operating systems.**

```bash
terraform version
```

```
bash: terraform: command not found
```

But it clearly works for you — the evidence is sitting in the repo. Look at the vendored provider paths:

```
infra/.terraform/providers/registry.terraform.io/hashicorp/aws/5.100.0/linux_amd64/...
```

`linux_amd64`. Those are Linux binaries. Terraform has only ever run here from **WSL** (Windows Subsystem for Linux), never from Windows. Confirming it:

```bash
wsl -e bash -lc "which terraform uv python3"
```

```
/usr/bin/terraform
/home/harshitrawat/.local/bin/uv
/usr/bin/python3
```

So the split is:

| Windows side | WSL Ubuntu side |
|---|---|
| `docker`, `kubectl`, `helm`, `aws` | `terraform`, `uv`, `python3` |

Claude Code runs on the **Windows** side. So any session that types a bare `terraform plan` gets "command not found" and may waste a while trying to reinstall something that isn't broken. The fix is a documented wrapper pattern:

```bash
wsl -e bash -lc "cd /mnt/c/Users/harshit.rawat/Documents/Projects/app-hub/infra && terraform plan"
```

Reading that command piece by piece:
- `wsl -e` — execute a command inside the WSL distro rather than opening a shell
- `bash -lc` — run bash as a **l**ogin shell (so `~/.local/bin` is on PATH — this is what makes `uv` findable) and take the **c**ommand from the next argument
- `/mnt/c/...` — WSL mounts your Windows `C:` drive here. Same files, different path. This is why both sides can work on the same project without copying anything.

### What each file does

**`CLAUDE.md`** — the operating manual for AI sessions. Eight sections: the objective (including a "drift test" question to ask before starting anything), the teaching rule, the repo layout, hard constraints, the WSL split, the read order, a finish-the-task checklist, and a pointer to known defects.

**`README.md`** — for humans. What the project is, an annotated directory tree, an AWS resource table, OS-tagged quick-start commands, and governance rules.

**`PROGRESS.md`** — the status board, in your requested format:

```markdown
| ID | Task | Status | Blocker | Next step |
|----|------|--------|---------|-----------|
| C-01 | Fix POST /links storing the wrong object | Not started | None | main.py:29 — change `links_db[next_id] = link` to `= new_link` |
```

The **blocker** column is the one that earns its keep. "Not started" tells you nothing about *why*. "Blocked — needs an owner decision on persistence" tells you the next action is a conversation, not typing.

Tasks are ID'd by phase — `P-` hygiene, `C-` correctness, `E-` end-to-end deploy, `R-` production readiness — so they can reference each other as dependencies.

**`learn/`** — this folder.

### Two real bugs the audit surfaced

Worth walking through, because they're both instructive.

**The `POST /links` bug** — [links-service/app/main.py:29](../links-service/app/main.py:29):

```python
@app.post("/links")
def createLink(link: LinkCreate):
    global next_id
    new_link = Link(id=next_id, **link.model_dump())   # builds the right object...
    links_db[next_id] = link                            # ...then stores the WRONG one
    next_id += 1
    return new_link                                     # ...and returns the right one
```

`LinkCreate` has no `id` field; `Link` does. Line 28 correctly constructs a `Link` with an id. Line 29 then stores `link` — the original `LinkCreate` — into the database. Line 31 returns `new_link`.

The reason this is nasty: **`POST` looks completely correct.** You send a link, you get back a proper response with an id. The bug only shows when you read the data back — `GET /links` and `GET /links/{id}` return records with no `id` field, because that's what actually got stored. A one-word fix (`link` → `new_link`), but a good illustration of why "the response looked right" isn't verification.

**The replicas bug** — this one is architectural, spanning two files:

```python
links_db: dict[int, Link] = {}     # main.py:5 — state lives in the process
```

```yaml
spec:
  replicas: 2                       # deployment.yaml — two independent processes
```

Two pods, each with its own `links_db` dictionary, sitting behind one Service that load-balances between them. Create a link — it lands on pod A. Read it back — you might hit pod B, which has never heard of it. Restart either pod and its data is gone entirely.

The concept underneath: **Kubernetes pods are ephemeral and interchangeable.** Anything you want to survive a restart, or be visible from any replica, has to live *outside* the pod — a database, a cache, a persistent volume. In-memory state is fine for a single-replica prototype and breaks the moment you scale. This needs a decision from you (drop to 1 replica as a stopgap, or add a real datastore), so it's logged as `C-03` rather than silently fixed.

## Gotchas

- **`git` at the root will mislead you.** Always `git -C <subdir>`. If a command reports a suspiciously unfamiliar repo, that's git having walked up past `app-hub/` into a parent.
- **The root docs aren't backed up.** `CLAUDE.md`, `README.md`, `PROGRESS.md`, and `learn/` are in no repository. Delete the folder and they're gone. Decide where they live (`P-01`).
- **Windows `python` is a trap.** `C:\...\WindowsApps\python.exe` is the Microsoft Store stub — it isn't a Python, it's a redirect to the store. Use `wsl ... python3`.
- **`terraform.tfstate` in `infra/` proves nothing.** It's a leftover stub from before the S3 backend migration: serial 1, zero resources. The real state is in S3. Don't read the local file to figure out what's deployed — that's what `E-01` exists to check properly.
- **`gh` isn't installed.** Any workflow assuming the GitHub CLI will fail. Web UI, or install it.
